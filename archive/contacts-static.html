三條會擋住你的硬約束

約束一 · name 是條件式必填

資料庫層有一條 CHECK 約束，名字叫 res_partner_check_name：

((type)::text = 'contact'::text AND name IS NOT NULL)
OR ((type)::text <> 'contact'::text)

只有 type='contact' 的記錄強制要有名字。地址型記錄（invoice、delivery）可以沒有 name。這就是為什麼 name 在欄位定義上不是 required——約束在表層而非欄位層，所以在 debug mode 的 Fields 清單裡看不到它。

約束二 · 沒有任何 UNIQUE 約束

res_partner 表除了主鍵之外沒有唯一鍵。資料庫層允許你匯入兩筆完全相同的聯絡人，重複匯入不會被擋。去重必須在匯入前自己做，或依賴 Odoo 匯入介面的 External ID 對應。

約束三 · DB 層 NOT NULL 只有四欄

id、autopost_bills、group_on、group_rfq。後三個都是 selection 且有預設值，匯入時不填也會自動帶入。換句話說，除了 name 那條 CHECK，資料庫幾乎不會攔你——資料品質完全靠匯入前把關。

debug mode 看不出來的事：三種計算欄位

這一節是我在準備這份文件時實測發現的，對導入很關鍵。store 這個旗標不足以判斷一個欄位能不能匯入，實際有三種狀態：

狀態能不能匯入例子
store=false不能，資料庫根本沒這一欄company_type、contact_address
compute + store=true + readonly=False可以，不填會自動算，填了以你的為準user_id（業務員）
compute + store=true不能，匯了也會被重算覆蓋commercial_partner_id、complete_name、commercial_company_name、partner_share
為什麼 debug mode 幫不上這個忙

ir_model_fields 有一個 compute 欄位，但它對全部 8469 個 state='base' 的欄位都是 NULL——它只記錄客製欄位的 compute 運算式。原生欄位的 compute 方法寫在 Python 裡，不進這張表。

所以在 debug mode 的 Fields 清單上，user_id（可匯）和 commercial_partner_id（不可匯）看起來一模一樣：兩個都是 store=true、required=false 的 many2one。要分辨只能讀原始碼，或用 Odoo 匯入介面的欄位下拉選單反查——匯入介面只列出實際可寫的欄位。

一個台灣導入會遇到的怪欄位

res.partner.bank 有一個 required=true 的欄位叫 l10n_us_bank_account_type（Bank Account Type，選項 checking / savings），來自 l10n_us 模組。它有預設值 checking，所以不會擋住匯入，但你的台灣銀行帳號都會被標記成美國的支票帳戶。這是這套環境同時裝了 l10n_us 與 l10n_tw 的副作用。

建議的匯入順序

注意

下面的順序是我從外鍵依賴關係推出來的建議，不是 Odoo 官方文件的規定。依賴關係本身（誰指向誰、哪些必填）是上面圖表的實查結果。

  1. 先確認不用建的：國家、州省已內建。台灣的 22 個縣市在 res.country.state 裡，先查名稱寫法與你的來源資料是否對得上。
  2. 建分類主檔：res.partner.category（標籤）、必要時補 res.partner.industry。標籤有 parent_id，可以先設計階層。
  3. 建人員：業務員必須先存在於 res.users，否則 user_id 無處可指。
  4. 建會計主檔：付款條件 account.payment.term。科目已隨 l10n_tw 建好。
  5. 匯公司型聯絡人：is_company=true、type='contact'、parent_id 留空。這一批必須有 name。
  6. 匯個人與子聯絡人：parent_id 指向上一步的公司。type='contact'，一樣必須有 name。
  7. 匯地址型記錄（若有需要）：type='invoice' 或 'delivery'，parent_id 指向公司。這批可以沒有 name。
  8. 匯銀行帳號：res.partner.bank，partner_id 必填，所以一定在聯絡人之後。

我沒能替你確認的部分

誠實標示，免得你當成已查證的事實：

  • 完整的可匯入欄位清單。我試著用原始碼掃描區分 compute 與非 compute 欄位，但掃描結果混入了同檔案內其他 model 的欄位，我不會拿一份可能有錯的清單給你當導入依據。上面圖上列出的欄位是逐一確認過的，但那不是全部 106 個。
  • ORM 層的 constraint。除了那條 SQL CHECK 之外，Odoo 還可能在 Python 的 @api.constrains 裡加驗證（例如 base_vat 對統一編號的檢查碼驗證）。那些不在資料庫裡，我沒有逐一清點。
  • 匯入時會觸發的自動行為。例如建立 partner 時 commercial_partner_id 怎麼算、parent_id 變動時子記錄的地址欄位會不會被同步覆寫。這些是 _compute 與 write 的邏輯，要讀原始碼才能確定。

前兩項如果你要，我可以繼續查到確定為止。第三項建議直接在這個 sandbox 上實測——建一筆、改一筆、看它變成什麼，比讀程式碼快。

psql -U odoo -d odoo-dev-19 -c "
-- res.partner 的欄位規模
SELECT count(*) FILTER (WHERE store) AS 有存的,
       count(*) FILTER (WHERE store AND required) AS 必填的
FROM ir_model_fields f JOIN ir_model m ON f.model_id=m.id
WHERE m.model='res.partner';

-- 表層約束（CHECK / UNIQUE 都在這）
SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint
WHERE conrelid='res_partner'::regclass;

-- 現有聯絡人的型態分布
SELECT type, count(*), count(*) FILTER (WHERE parent_id IS NOT NULL) AS 有母記錄
FROM res_partner GROUP BY type;"

UI 上的等價路徑：debug mode 開啟後的 設定 → 技術 → 資料庫結構 → 欄位，篩選 Model 為 res.partner。但記得上面那節——表層的 CHECK 約束和 compute 的可寫性，這個畫面都看不到。
