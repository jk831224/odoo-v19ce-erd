說明

實體索引

點任一項飛到該實體並放大。不在目前視圖的會自動切過去，不必先知道它畫在哪一張。

這張圖現在涵蓋什麼

分成四張視圖，不是一張全景。總覽只畫模組方塊與接縫，點方塊進入該視圖；聯絡人與商品主檔各 12 個實體，採購 3 個。單張畫滿 24 個實體時全圖適配只剩 2.8px，視圖切分就是為了解決這件事。

標題寫「全景圖」，但只有三塊。共 27 個實體。Odoo 19 CE 的完整 model 數量遠大於此，不要把這張圖當成完整的資料庫地圖。

第一塊 · 聯絡人：res.partner 為中心，加上 res.country、res.country.state、res.city、res.partner.category 與其 m2m 中介表、res.partner.industry、res.users、res.company、res.partner.bank、account.payment.term、account.account。

第二塊 · 商品主檔：product.template / product.product 雙層，加上 product.category 分類樹、uom.uom、product.uom 條碼表、product.supplierinfo 供應商價目，以及產生變體的四層屬性系統（product.attribute、product.attribute.value、product.template.attribute.line、product.template.attribute.value）與兩張中介表。

第三塊 · 採購：purchase.order 與 purchase.order.line 兩層，加上一張連到商品屬性值的 m2m 中介表。purchase.* 在這套環境只有 6 個 model，其中 purchase.bill.union 是 SQL view、purchase.report 是報表，真正要畫的就這三個。

三塊的接縫：product.supplierinfo.partner_id 指向 res.partner，且是 required + cascade，這是商品與聯絡人唯一的直接連結。採購同時接住兩邊——purchase.order.partner_id 指向供應商（required + restrict）、purchase.order.line.product_id 指向商品變體，另有 payment_term_id 接到 account.payment.term。各視圖裡只有主鍵的框都是邊界節點，標示「這裡接到別的地方」，完整定義在它自己的視圖。

已畫但不在這一張裡：銷售鏈（sale.order → stock.picking → account.move 與其明細層，含 9 個實體）在同一資料夾的 sale-chain.html。那張圖的 res.partner 與 product.product 就是這裡的同一批記錄。

尚未畫：庫存內部（stock.quant、stock.location 階層、補貨鏈）、會計側的對帳與稅務、價目表規則（product.pricelist.item）、商品標籤、製造、專案、人資，以及所有 l10n_* 在地化模組加上的欄位。

資料來源：odoo-dev-19 資料庫的 ir_model_fields 與 PostgreSQL 系統表，74 個模組已安裝（含 l10n_tw、base_vat）。查詢日期 2026-08-13。裝不同的模組會得到不同的欄位集合，這張圖反映的是這一套環境。

三條會擋住你的硬約束
name 是條件式必填

資料庫層有一條 CHECK 約束 res_partner_check_name：

((type)::text = 'contact'::text AND name IS NOT NULL)
OR ((type)::text <> 'contact'::text)

只有 type='contact' 強制要有名字，地址型記錄（invoice、delivery）可以沒有。這就是為什麼 name 在欄位定義上不是 required：約束在表層而非欄位層，所以 debug mode 的 Fields 清單看不到它。

沒有任何 UNIQUE 約束

res_partner 表除了主鍵之外沒有唯一鍵。資料庫允許你匯入兩筆完全相同的聯絡人，重複匯入不會被擋。去重必須在匯入前自己做，或依賴匯入介面的 External ID 對應。

DB 層 NOT NULL 只有四欄

id、autopost_bills、group_on、group_rfq。後三個都是 selection 且有預設值，不填也會自動帶入。除了 name 那條 CHECK，資料庫幾乎不會攔你。資料品質完全靠匯入前把關。

值Odoo 標籤seqname 必填

invoiceInvoice1否
deliveryDelivery2否

目前資料庫裡 45 筆聯絡人全部是 contact，一筆 invoice 或 delivery 都沒有。如果客戶有「帳單地址與收貨地址不同」的需求，那是這個環境還沒出現過的資料型態，值得先手動建一筆走完流程。

商品雙層：variant 上有 15 個假欄位

product.template 有 71 個 store 欄位，product.product 只有 37 個。差距不是因為變體資訊少，而是因為變體層上有 15 個欄位在資料庫裡根本不存在，它們全部 related 到 product_tmpl_id.*：

name、list_price、categ_id、uom_id、type、tracking、company_id、sale_ok、purchase_ok、description_sale、taxes_id、supplier_taxes_id、seller_ids、attribute_line_ids、product_variant_ids

連商品名稱與售價都只存在 template 層。ORM 會自動穿透，所以 UI 上兩邊都看得到、也都能編輯（寫進去實際是寫到 template）。但如果你直接下 SQL 查 product_product.name，那一欄不存在。

對導入的意思很直接：商品的內容匯到 product.template，不是 product.product。變體是 Odoo 依屬性自動產生的，不是你匯出來的。目前這套環境有 37 個 template 對 47 個 variant。

Odoo 19 把計量單位改版了

uom.category 這個 model 在 19 已經不存在。如果你手上有 18 或更早的匯入範本，裡面的單位分類欄位在這裡無處可填。

新的結構是單位之間直接相對參照：uom.uom.relative_uom_id 指向另一個 uom.uom（標籤是 Reference Unit），搭配 relative_factor（Contains，required）表示換算倍數，並用 parent_path 維護階層索引。換句話說，單位形成一棵樹，而不是分組在 category 底下。

另外多出一張 product.uom（Link between products and their UoMs），三個必填欄位是 barcode、product_id、uom_id。它讓同一個商品的不同包裝單位各有自己的條碼，取代舊版的 product.packaging。注意它指向 product.product（變體層），不是 template。

...template.attribute.line這個商品有哪個屬性—
...template.attribute.value這個商品的這個值，可單獨加價—

前兩層是全域共用的字典，後兩層是綁在特定商品上的。變體本身則定義在中介表 product_variant_combination：一筆 product.product 對上一組 ...template.attribute.value，就是「紅色 + L 號」那一件。

product.attribute.create_variant 是 required 的 selection，它決定這個屬性到底會不會實際產生變體記錄。有些屬性只是顯示用，不該讓變體數量爆炸。

product_variant_combination 的兩個外鍵方向不對稱：對 product.product 是 cascade（刪變體，組合記錄跟著消失），對 ...template.attribute.value 是 restrict（屬性值只要還被任何變體用著就刪不掉）。

debug mode 看不出來的事

store 這個旗標不足以判斷一個欄位能不能匯入，實際有三種狀態：

狀態能匯嗎例子
store=false不能，DB 沒這欄company_type
compute + store + readonly=False能，不填自動算user_id
compute + store不能，會被重算覆蓋commercial_partner_id、complete_name
為什麼 debug mode 幫不上這個忙

ir_model_fields 有一個 compute 欄位，但它對全部 8469 個 state='base' 的欄位都是 NULL，因為它只記錄客製欄位的運算式。原生欄位的 compute 方法寫在 Python 裡，不進這張表。

所以在 Fields 清單上，可匯的 user_id 和不可匯的 commercial_partner_id 看起來一模一樣：都是 store=true、required=false 的 many2one。要分辨只能讀原始碼，或用匯入介面的欄位下拉選單反查，它只列出實際可寫的欄位。

聯絡人的匯入順序

下面的順序是從外鍵依賴推出來的建議，不是 Odoo 官方文件的規定。依賴關係本身（誰指向誰、哪些必填）是圖上的實查結果。

  1. 先確認不用建的：國家、州省已內建。台灣 22 個縣市在 res.country.state，先查名稱寫法跟你的來源資料對不對得上。
  2. 建分類主檔：res.partner.category、必要時補 res.partner.industry。標籤有 parent_id，可以先設計階層。
  3. 建人員：業務員必須先存在於 res.users，否則 user_id 無處可指。
  4. 建會計主檔：付款條件 account.payment.term。科目已隨 l10n_tw 建好。
  5. 匯公司型聯絡人：is_company=true、type='contact'、parent_id 留空。這批必須有 name。
  6. 匯個人與子聯絡人：parent_id 指向上一步的公司，type='contact'，一樣必須有 name。
  7. 匯地址型記錄：type='invoice' 或 'delivery'，parent_id 指向公司。這批可以沒有 name。
  8. 匯銀行帳號：res.partner.bank，partner_id 必填，一定在聯絡人之後。
商品主檔的匯入順序

同樣是從外鍵依賴推出來的建議，不是官方規定。依賴關係本身是圖上的實查結果。這一段假設聯絡人已經匯完，因為供應商價目需要 res.partner 先存在。

  1. 分類樹：product.category，只有 name 必填。有 parent_id，父分類要先建。注意它是 cascade，之後刪父分類會連子分類一起消失。
  2. 計量單位：uom.uom，必填 name 與 relative_factor。19 是階層結構，relative_uom_id 指向的參考單位要先存在。內建已有 30 筆。
  3. 屬性字典：先 product.attribute（必填 name、create_variant、display_type），再 product.attribute.value（必填 name、attribute_id）。這兩層是全域共用的。
  4. 商品本體：product.template，必填 name、uom_id、type、tracking、service_tracking。所有商品內容都匯在這一層。
  5. 商品的屬性設定：...attribute.line 與 ...attribute.value。實務上很少直接匯：在 UI 上替商品掛屬性時 Odoo 會自己建，變體也在這一步自動產生，不需要你匯 product.product。
  6. 供應商價目：product.supplierinfo，六個必填欄位，需要 res.partner 與 product.template 都已存在。
  7. 條碼：product.uom，必填 barcode、product_id、uom_id。它指向變體，所以一定在變體產生之後。

不要匯 product.product。它唯一的必填欄位是 product_tmpl_id，其他 15 個看得到的欄位都是 template 的投影。變體該由屬性設定自動生成，手動建立會與屬性組合對不上。

採購行的 product_id 是條件式必填

ir_model_fields 說 purchase.order.line 只有四個必填：name、product_qty、price_unit、order_id。那不是全部。真正的規則在兩條表層 CHECK 裡，和 res.partner.name 是同一類坑。

purchase_order_line_accountable_required_fields
  display_type IS NOT NULL OR is_downpayment
  OR (product_id IS NOT NULL AND product_uom_id IS NOT NULL
      AND date_planned IS NOT NULL)
purchase_order_line_non_accountable_null_fields
  display_type IS NULL
  OR (product_id IS NULL AND price_unit = 0
      AND product_uom_qty = 0 AND product_uom_id IS NULL
      AND date_planned IS NULL)

合起來是：一般行（display_type 為 null 且非預付款）必須有 product_id、product_uom_id、date_planned；分節與備註行（display_type 為 line_section、line_subsection 或 line_note）反過來，那三欄必須留空，price_unit 與 product_uom_qty 必須是 0。

實查 23 行全部有 product_id，因為現有資料都是一般行。若照 ir_model_fields 的必填清單準備匯入欄位，一般行會被資料庫直接擋下。

line_subsection 這個值沒有官方繁中翻譯，UI 上會顯示英文。

採購的匯入順序

一樣是從外鍵依賴推出來的建議，不是官方規定。依賴關係本身是實查結果。這一段假設聯絡人與商品都已匯完。

  1. 先確認圖外那兩個必填：purchase.order 必填 currency_id（指向 res.currency）與 picking_type_id（指向 stock.picking.type），兩者都是 restrict。它們不在這張圖上，但沒有就開不了單。
  2. 採購單頭：purchase.order，六個必填 —— name、date_order、company_id、currency_id、partner_id、picking_type_id。partner_id 要的是供應商，res.partner 得先存在。
  3. 採購明細：purchase.order.line，order_id 是 cascade，單頭刪掉明細跟著消失。一般行還要滿足上面那兩條 CHECK，所以 product.product 與 uom.uom 也得先在。

單號沒有唯一約束。purchase_order 上查不到任何 UNIQUE 或 CHECK（pg_constraint 回 0 筆），name 重複資料庫不會擋。重跑匯入會產生一批同號的單，去重要在來源端做。

我沒能替你確認的部分

誠實標示，免得你當成已查證的事實：

  • 完整的可匯入欄位清單。我試著用原始碼掃描區分 compute 與非 compute 欄位，但掃描結果混入了同檔案內其他 model 的欄位。圖上列出的欄位是逐一確認過的，但那不是全部 106 個。
  • ORM 層的 constraint。除了那條 SQL CHECK，Odoo 還可能在 @api.constrains 裡加驗證（例如 base_vat 對統一編號的檢查碼）。那些不在資料庫裡，我沒有逐一清點。
  • 匯入時觸發的自動行為。例如 commercial_partner_id 怎麼算、parent_id 變動時子記錄的地址會不會被同步覆寫。要讀原始碼才能確定。

前兩項要的話我可以查到確定為止。第三項建議直接在 sandbox 實測：建一筆、改一筆、看它變成什麼，比讀程式碼快。
