怎麼讀這張圖

關係線上的標籤是外鍵欄位名，不是關係名稱。這是刻意的——你在 debug mode 的 Fields 清單裡看到的就是這個名字，兩邊對得上。

線的左端記號決定了刪除行為的嚴重性。||（恰好一個）代表那個外鍵是 required，沒有它這筆資料根本建不起來；|o（零或一）代表可以留空。

on_delete意思本圖中的例子
cascade父記錄刪掉，子記錄一起消失sale.order.line.order_id、account.move.line.move_id、product.product.product_tmpl_id
restrict還有人指著就不准刪sale.order.partner_id、stock.move.product_id
set null父記錄刪掉，欄位變空，子記錄留著stock.move.picking_id、stock.picking.sale_id

圖上值得注意的幾件事

一、res.partner 有三條線通往同一張 sale.order。

partner_id、partner_invoice_id、partner_shipping_id 三個都是 required + restrict。它們是三個獨立的外鍵，語義是下單方、開票方、收貨方。原生就支援三者不同——不需要為此加欄位。

二、sale.order.line.product_id 不是必填。

訂單明細可以沒有商品。這是給區段標題與備註行用的（display_type 之類）。但 stock.move.product_id 是 required——庫存移動必須有東西在動。同一個欄位名，兩邊的必填性相反。

三、訂單與發票之間唯一的實體關聯在明細層。

sale.order.line 與 account.move.line 之間是多對多，圖上依 ERD 慣例展開成中介表 sale_order_line_invoice_rel。它是真實存在的資料庫表，沒有 id 欄位，主鍵是 (invoice_line_id, order_line_id) 複合鍵，兩個外鍵都是 ON DELETE CASCADE——刪掉訂單明細，開票關聯記錄跟著消失，但發票明細本身留著。

單頭層的 sale.order.invoice_ids 是 store=false 的計算欄位，資料庫裡沒有這個欄位，所以圖上沒有 sale.order 直通 account.move 的線。

四、res.partner 的 name 不是 required。

它在資料庫層沒有 NOT NULL。res.partner 僅有的三個必填欄位是 autopost_bills、group_on、group_rfq，全是 selection。名稱的約束在 ORM 層，不在 schema 層。

五、圖內範圍有十條自我參照的 many2one，另有一組自我多對多。

Odoo 大量用自我參照處理「同類型但有前後關係」的資料。下表的標籤欄位是 Odoo 自己的 field_description，不是我的翻譯：

圖上把同一個實體的多條自我參照畫成一條線、標籤以斜線並列（例如 res.partner 那條寫著 parent_id / commercial_partner_id）。這是為了繞開 Mermaid 的一個限制：同一對實體之間畫多條自我參照時，它只會渲染最後一條的標籤，其餘的標籤會消失。實際關係數以上表為準。

唯一的自我多對多是 stock.move 的補貨鏈，中介表 stock_move_move_rel，兩個方向分別叫 move_orig_ids（Original Move）與 move_dest_ids（Destination Moves）。Odoo 的 help 說明它用於串接前後的庫存移動。

這張圖沒有畫的

  • 圖外實體。res.company、res.currency、account.journal、stock.location、uom.uom、stock.picking.type 沒有畫成實體，但它們的外鍵已列在屬性中，標記為「圖外」。全部都是 required。
  • 非必填的一般欄位。依你指定的粒度，只列了主鍵、外鍵、必填欄位。sale.order 實際上有 100 個以上的欄位。
  • 指向圖外的非必填外鍵。例如 sale.order.journal_id、account.move.line.tax_line_id。全列會讓每個實體長到讀不動。
  • 一對多的反向欄位。ERD 的關係線已經表達了一對多，所以 order_line、move_ids、line_ids 這些 one2many 沒有另外列成屬性——它們在資料庫裡也沒有實體欄位。
  • 兩組沒有展開的多對多。account.move 的調整分錄（中介表 adjusting_entries__account_move，欄位 adjusting_entries_move_ids / adjusting_entry_origin_move_ids）與 product.template.optional_product_ids 選配商品（中介表 product_optional_rel）都是 store=true 的真實中介表，但不在銷售主線上，沒有畫進來。

自己重跑這份資料

這張圖的每一條線都來自下面這個查詢。改 model 清單就能得到別的範圍：

psql -U odoo -d odoo-dev-19 -c "
WITH s AS (SELECT unnest(ARRAY['sale.order','sale.order.line']) AS m)
SELECT m.model, f.name, f.ttype, f.relation, f.required, f.on_delete, f.store
FROM ir_model_fields f JOIN ir_model m ON f.model_id=m.id
WHERE m.model IN (SELECT m FROM s) AND f.store IS TRUE
ORDER BY m.model, f.required DESC, f.name;"

UI 上的等價路徑是 debug mode 開啟後的 設定 → 技術 → 資料庫結構 → 欄位，或任一畫面的 debug 選單 → Fields。
